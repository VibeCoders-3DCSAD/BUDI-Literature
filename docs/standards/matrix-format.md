# Literature Review Matrix Format

`docs/literature-review-matrix.md` is a **generated view**, not a database. It is
rebuilt from three normalized sources and must never be hand-edited.

Regenerate with:

```bash
python3 scripts/build_matrix.py           # build matrix + long tables + validation
python3 scripts/build_matrix.py --check   # validate only, exit 1 on any error
```

## Sources of truth

| Column group | Source | Authority |
| :--- | :--- | :--- |
| Bibliographic | `literature/conversions/metadata.json` | Citation authority. Page-1 verified. |
| Relevance | `scores/index.json` | Generated by `scripts/score.py` from `config/modules.yaml`. |
| Extraction | `{stem}_summarized.json` | Schema: `docs/standards/summary-format.md`. |

Nothing in the matrix may be written by hand. If a value is wrong, fix it in the
source above and re-run the builder — a direct edit to the matrix is lost on the
next build.

## Why 17 columns and not 56

The predecessor matrix had 56 columns and 2 rows of 93 papers, at roughly 11 KB
per row. Nineteen percent of its cells were `Not reported` or `Not applicable`,
and the long cells (`Key_Findings`, `Direct_Citations_Statements`,
`Statistical_Evidence`, `Gaps_Identified`) held 800–900 characters each. At 93
papers that is a 1 MB table that cannot be diffed, reviewed, or read.

The rule: **a column earns its place only if it is filled for most papers.** A
column that is usually empty does not belong in the matrix; its content, when
present, belongs in the per-paper summary.

## Columns

In this exact order.

| # | Column | Source | Rule |
| ---: | :--- | :--- | :--- |
| 1 | `paper_id` | stem | The corpus stem. Primary key. Never blank. |
| 2 | `first_author` | metadata | `First_Author` if recorded, else derived from the stem author segment. |
| 3 | `year` | metadata | Publication year as printed. |
| 4 | `title` | metadata | Sentence case, no trailing period. |
| 5 | `venue` | metadata | Journal or issuing body. `Unverified` suffix when `venue_unverified`. |
| 6 | `doi` | metadata | Normalized, no line-break artifacts. `Not reported` when absent. |
| 7 | `type` | summary, else metadata | Controlled list below. |
| 8 | `designation` | stem prefix | `local` / `international` / `algorithm`. |
| 9 | `tier` | scores | `crucial` / `supporting` / `cull`. |
| 10 | `best_module` | scores | Best-scoring `config/modules.yaml` module id. |
| 11 | `relevance` | scores | Combined score, 3 decimals. |
| 12 | `tags` | modules + designation | Controlled namespace below, `; `-separated. |
| 13 | `design` | summary | Study design label as the paper states it. |
| 14 | `sample` | summary | N and unit as reported. |
| 15 | `key_finding` | summary `tldr` | One sentence. Capped at 200 characters. |
| 16 | `gap` | summary `limitations` | First acknowledged limitation, verbatim. Capped at 200 characters. |
| 17 | `status` | derived | `extracted` / `not extracted`. |

Rows are sorted by year descending, then `paper_id` ascending. Cell content is
capped at 200 characters with `...` so no row can dominate the file; the
uncapped value always remains in the summary JSON.

## Controlled values

`type` is one of: `journal-article`, `conference-paper`, `book`, `book-chapter`,
`thesis`, `preprint`, `report`, `working-paper`, `dataset`, `dashboard`,
`webpage`, `other`. Anything else is a validation error.

`designation` maps from the stem prefix: `L--` → `local`, `I--` →
`international`, `A--` → `algorithm`. Legacy compound prefixes (`AI--`, `IA--`,
`AL--`, `LA--`) resolve to `algorithm`.

`status` is `extracted` when the summary JSON parses and is non-empty,
`not extracted` otherwise. A `not extracted` row still shows its bibliographic
and relevance columns; its extraction columns read `Not reported`. This is the
honest state of a corpus where most papers are unsummarised, and it is visible
rather than hidden behind blank cells.

## Tag namespace

Reuses `config/modules.yaml` module ids as the controlled vocabulary. A paper is
tagged with every module whose combined score clears `tiers.supporting_min`
(default 0.30), so a paper relevant to several leaves is visible in all of them.

| Prefix | Source | Example |
| :--- | :--- | :--- |
| `theme/` | `config/modules.yaml` module id, top 5 by score | `theme/forecasting` |
| `scope/` | Stem prefix | `scope/local` |
| `method/` | Summary `study_design`, mapped to a controlled list | `method/slr` |
| `status/` | Extraction state | `status/not-extracted` |
| `quality/` | `venue_unverified` / missing DOI | `quality/metadata-partial` |

`method/` maps the free-text `study_design` onto one controlled value, because a
tag cell that repeats a 200-character sentence is not a tag. The mapping is
ordered, first match wins: `slr`, `meta-analysis`, `literature-review`,
`qualitative`, `survey`, `experimental`, `benchmark`, `design-science`,
`dataset`, `simulation`, `conceptual`, `other`. Add a value to `DESIGN_METHODS`
in `scripts/build_matrix.py` when a design has no home.

Adding a theme means editing `config/modules.yaml` and re-running
`scripts/score.py`, exactly as the rest of the pipeline already does. There is no
second vocabulary to keep in sync.

A paper that clears more than five modules shows its top five by score plus
`theme/+Nmore`. Broad systematic reviews legitimately clear eighteen modules, and
an eighteen-tag cell is exactly the sparse-cell problem this format exists to
avoid. The complete per-module ranking for every paper is in
`scores/index.json`, and `scores/report.md` ranks each module separately.

## Missing values

| Situation | Token |
| :--- | :--- |
| Source has no value | `Not reported` |
| Field does not apply to this design | `Not applicable` |
| Recorded but known unreliable | `Unverified` (with the reason in the summary) |

Never blank, never `N/A`, never `unknown`, never `-`.

## Validation

`--check` exits non-zero if any rule fails. Each rule exists because that failure
has already occurred in this repository.

| Rule | Failure it prevents |
| :--- | :--- |
| DOI matches `^10\.\d{4,9}/\S+$`, in metadata **and** in the summary | The `10.1 109/ACCESS.2025.3587231` line-break artifact. A summary-only DOI is checked too, so a malformed value cannot hide behind a well-formed metadata entry. |
| Every `paper_id` resolves in `conversions/` **and** `scores/index.json` | `A--DeyArefin-2025` was converted but never scored. |
| No duplicate DOI | Same paper entered twice under different stems. |
| No duplicate normalized title | Same paper under a different stem or year. |
| Stem year == metadata year | Stale stem after a metadata correction. |
| Summary `year` / `title` / `doi` agree with `metadata.json` | A summary silently re-deriving bibliographic metadata the sidecar already verified. `metadata.json` is the authority; the summary is the error. |
| `type` in the controlled list | Vocabulary drift between papers. |
| No empty cells; only approved tokens | Silent blanks read as "no limitation reported". |
| Same `outcome` + `metric` → one `value` per paper | One measurement re-reported as two numbers. |
| A figure quoted in a `limitations` discrepancy is absent from `effects[]` | A discrepancy silently reconciled during extraction. |

DOI comparison is normalized — lowercased, with a `https://doi.org/` prefix
stripped — so a case difference or a resolver URL is not reported as a conflict.

Both effect rules key on `outcome` **and** `metric` together, because `accuracy`
legitimately holds four different values in a comparison table, one per model,
and the `outcome` field is what tells them apart. Only a repeat of the *same*
measurement under a different number is a discrepancy.

A flagged conflict is a **finding about the paper, not about the extraction**.
`A--Aldrees-2025` reports 14.03% and 13.28% in its abstract against 14.82% and
13.63% in its conclusion, and all four are genuine. The summary keeps all four
with their locators and records the contradiction in `limitations`; the validator
reports it and must never pick a winner. Should someone later drop a figure from
`effects[]` while leaving the discrepancy claim standing, the second rule fires.

The fill-rate rule is suppressed below 10 extracted rows — below that, per-column
fill rates are noise and would produce a false verdict.

## Long tables

Evidence that does not fit a table cell lives in its own generated file, one
record per line item:

| File | Record | Source field |
| :--- | :--- | :--- |
| `scores/quotes.json` | `{paper_id, text, locator, theme}` | summary `quotes[]` |
| `scores/effects.json` | `{paper_id, outcome, metric, value, ci, p, locator}` | summary `effects[]` |

Both are projections of the per-paper summaries, not independent stores. Edit the
summary, re-run the builder.
